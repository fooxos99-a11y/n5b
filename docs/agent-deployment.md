# النشر والإصدارات

تُقرأ هذه التعليمات عند طلب نشر أو تجهيز إصدار فقط. تجهيز الإصدار لا يصرّح بالرفع. قواعد AGENTS.md الأساسية سارية.

## سياسة النشر وملف `data1.yml`

### الأصل

- لا ترفع أو تنشر أو تعيد تشغيل خدمة أو تعدّل سيرفرًا خارجيًا إلا بطلب صريح يتضمن مثلًا: «ارفع»، «انشر»، `deploy` أو `release`.
- أوامر «عدّل»، «أصلح»، «جهّز»، «اختبر» أو «ابنِ» لا تعني النشر.

### قراءة ملف النشر

- جميع بيانات الاستضافة والرفع الخاصة بالمشروع توجد في ملف واحد بجذر المشروع اسمه `data1.yml`.
- لا يحتوي `AGENTS.md` أي بيانات استضافة خاصة.
- لا تقرأ `data1.yml` ولا تتحقق من وجوده إلا عند طلب نشر صريح.
- عند طلب النشر، اقرأه مرة واحدة واعتبره مصدر الحقيقة الوحيد للوجهات والأسماء البديلة والنطاقات والبناء والمسارات والخدمات والمنافذ وقواعد البيانات وروابط التحقق.
- لا تستنتج بيانات النشر من اسم المجلد أو Git أو الذاكرة أو مشروع آخر.

### إذا كان الملف مفقودًا

عند طلب النشر فقط، إذا لم يوجد `data1.yml`:
1. أنشئه بهذا المحتوى:
   ```yaml
   version: 1
   targets: {}
   ```
2. لا تخمّن أي بيانات.
3. أوقف النشر واذكر أن بيانات الوجهات تحتاج إلى تعبئة.

### تحديد الوجهات

- موقع «نخب» على المسار `/n5b` هو الوجهة الأساسية للمشروع، وهو مستقل تمامًا عن المشروع الذي نُسخ منه ومواقعه على نفس السيرفر: لا تنشر عليها ولا تشاركها قاعدة بيانات أو خدمة أو مسارًا أو جلسات أو مستودع Git.
- إذا سمّى المستخدم وجهة، طابقها مع المعرّف أو `display_name` أو `aliases` وانشر عليها فقط.
- إذا سمّى عدة وجهات، انشر على المذكورة فقط.
- إذا قال «ارفع التعديلات» دون تحديد، انشر على جميع الوجهات التي تحتوي `enabled: true`.
- إذا كانت وجهة واحدة مفعّلة، انشر عليها وحدها.
- لا تنشر على وجهة غير مفعّلة أو غير معرّفة أو ملتبسة، ولا تعتبر عدم المطابقة نشرًا للجميع.

### قبل التنفيذ

لكل وجهة مستهدفة:
- تحقق من اكتمال بيانات وطريقة النشر الفعلية.
- تحقق من أمر البناء ومسار السيرفر والخدمة والنطاق ووسيلة الاتصال.
- تحقق من عزل المنافذ وقواعد البيانات والتخزين والجلسات عن بقية الوجهات.
- عند تغييرات قاعدة البيانات، خذ Backup مستقلًا وتأكد من وجود rollback مناسب.
- إذا نقصت بيانات أساسية، لا تخمّن ولا تبدأ نشرًا جزئيًا إلا بطلب صريح.

### النشر المتعدد

- حدّد كل الوجهات أولًا وتحقق من جاهزيتها.
- شغّل الاختبارات المشتركة، ثم build مستقلًا لكل وجهة حسب بياناتها.
- تحقق من نجاح builds قبل الرفع.
- ارفع ناتج كل وجهة إلى مسارها فقط، ثم أعد تشغيل خدمتها وتحقق من health URL الخاص بها.
- لا تعتبر نجاح وجهة دليلًا على نجاح غيرها.
- لا تخلط artifacts أو قواعد البيانات أو الملفات أو الجلسات بين الوجهات.
- عند الفشل، أوقف ما يمكن إيقافه بأمان ونفّذ rollback المعرّف إن توفر، ثم اذكر حالة كل وجهة بدقة.

## منتج نخب

- المشروع يحتوي منتجًا واحدًا فقط باسم «نخب» بهوية موحدة للويب وAndroid وiOS.
- حافظ على اسم نخب وشعاراته وأيقوناته وروابطه وإعداداته المركزية، ولا تنشئ علامات تجارية أو تطبيقات إضافية دون طلب صريح جديد.
- معرّف التطبيق `applicationId` و`Bundle ID` هو `sa.nukhab.app`، ولا تخمّن معرفات الحزم أو بيانات المتاجر.
- يجب أن ينتج مسار الإصدار حزمتين أصليتين لنخب: Android وiOS، مع اختبار كل منصة بصورة مستقلة.
- تبقى سياسة النشر أعلاه سارية: لا يُرفع التطبيق إلا بطلب صريح، وتبقى `data1.yml` مصدر الحقيقة لوجهات وأوامر وأسرار النشر.

## وصفات إصدار نخب

- عند طلب النشر، تعامل مع الموقع وAndroid وTestFlight وApp Store كوجهات مستقلة، ولا تعتبر نجاح إحداها نجاحًا للبقية.
- احفظ أوامر البناء، مسارات الحزم، النطاق، `applicationId`، `Bundle ID`، المعرّفات وروابط التحقق في `data1.yml` فقط.
- لا تحفظ كلمة مرور أو مفتاح Apple أو Google أو ملف حساب خدمة داخل `AGENTS.md` أو Git؛ يحفظ في مدير الأسرار، ويذكر في `data1.yml` اسم متغير السر فقط.
- Android: نفّذ `npm run native:android` ثم أنشئ حزمة AAB موقعة واختبرها قبل الرفع إلى مسار الاختبار المحدد في `data1.yml`.
- iOS: استخدم Expo EAS Build لمشروع Capacitor/Xcode الأصلي بعد تهيئته والتحقق من التوقيع، ثم EAS Submit لرفع البناء الجديد إلى TestFlight. تجهيز محلي قد يسبق EAS عند الحاجة؛ لا تستخدم GitHub Actions ولا ترفع للعامة دون أمر مستقل.
- الموقع: نفّذ بوابة الجودة والبناء المعرّف للوجهة، ثم ارفع الناتج إلى المسار المحدد وأعد تشغيل الخدمة وتحقق من health URL.

## التحويل إلى EAS ونشر VPS دون GitHub Actions — 6 نوفمبر 2026

- تم إلغاء مهام GitHub Actions لهذا المستودع عمدًا لمنع استهلاك دقائق GitHub. **ممنوع إعادة إنشائها أو تشغيلها** للنشر أو البناء أو الاختبارات الدورية دون موافقة صريحة.
- «نخب» مشروع **Capacitor + Vite** وليس Expo/React Native؛ لا تحوّل التطبيق إلى React Native ولا تنفّذ `expo prebuild`. حافظ على تطبيق المتجر الحالي ومعرّف iOS وAndroid: `sa.nukhab.app`، وشهاداته وقدراته والإشعارات وCapacitor plugins وSQLite.
- Expo EAS Build يدعم المشاريع الأصلية غير Expo، لكن إعداد هذا المشروع لم يُختبر بعد. يجب على الوكيل، في المهمة الأولى المصرَّح بها لترحيل البناء، فحص `ios/App/App.xcodeproj` وSwift Package Manager وإعدادات التوقيع وبنية مجلد `ios`، وقراءة الوثائق الرسمية https://docs.expo.dev/build/introduction/ وhttps://docs.expo.dev/custom-builds/get-started/ وhttps://docs.expo.dev/submit/ios/ .
- جهّز EAS CLI وتكوين التطبيق الحالي `app.json` و`eas.json` و**custom build** ملائم لخطوات `npm run build:mobile` و`cap sync ios` وXcode، بما في ذلك معالجة مشكلات `pod install` وSwift Package Manager. لا تضع مفاتيح Apple في Git، ولا تستخدم اسم provisioning قديمًا من GitHub Action إذا أصبح غير صالح لإعدادات EAS.
- اربط فقط بحساب Expo الذي سجّل فيه المستخدم، وبسجل App Store Connect **للتطبيق الحالي**، ثم اضبط التوقيع في EAS Submit. لا تخمّن `projectId` أو `ascAppId` أو شهادات iOS، واطلب تدخل المستخدم فقط للمصادقة والموافقات الضرورية.
- عند قول المستخدم **«ارفع آخر تعديل للآيفون»** بعد اكتمال التهيئة والاختبارات: خذ **أحدث الملفات الموجودة محليًا** بما فيها غير المرفوعة إلى GitHub، وتأكد أنها غير مستثناة من رفع EAS، ثم ابنِها على Expo EAS و**ارفع الناتج نفسه** إلى TestFlight فقط. أرجع روابط build وsubmit والحالة الفعلية؛ لا تدّع النجاح قبل التأكد. لا ترفع إلى متجر App Store العام إلا بأمر مستقل.
- عند قول المستخدم **«ارفع الموقع»**: انشر مباشرةً من الجهاز المحلي إلى VPS عبر SSH/SFTP أو حزمة النشر الحالية الموجودة في `scripts/web-release`، باستخدام وجهة وأسرار `data1.yml` المعتمدة فقط. اختبر التطبيق وابنِه محليًا، وارفع الحزمة إلى المسار الصحيح باستخدام آلية إصدار ذرية أو rollback، وتحقق من الصحة. GitHub ليس وسيط نشر ولا يلزم `git push`. حافظ على عزل قواعد البيانات وعدم نقل الأسرار.
- عند قول **«ارفع آخر التعديلات»** دون تحديد ويب أو iOS، التزم بقواعد تحديد الوجهات الموجودة أعلاه ولا تفترض أن الطلب إذن لنشر جميع المتاجر.
- عدم وجود مفاتيح SSH على جهاز الوكيل أو اتصال Expo/Apple لا يبرر الرجوع إلى GitHub Actions؛ اشرح فقط خطوة التفويض اللازمة دون كشف المفاتيح.
