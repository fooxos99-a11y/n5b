# المكالمات على استضافتك باستخدام LiveKit

نخب يتصل بخادم LiveKit الخاص بك عبر WSS. لا يوجد مؤقت لإنهاء المكالمة داخل التطبيق؛ مدة استمرارها تعتمد على بقاء الخادم والشبكة والأجهزة متصلة. رمز الدخول صالح لخمس دقائق لبدء الاتصال، ويجدد LiveKit رموز المشاركين المتصلين. هذه الصلاحية لا تحدد مدة المكالمة.

## تجهيز الخادم

استخدم مولّد الإعداد الرسمي وخطوات [تثبيت LiveKit على خادم افتراضي](https://docs.livekit.io/transport/self-hosting/vm/). اختر نسخة إصدار محددة واحتفظ بنسخة من الإعداد السابق قبل التحديث. يلزم عنوان عام لخادم الإشارة وعنوان TURN، وشهادات TLS موثوقة، وتوجيه DNS إلى الخادم الفعلي. لا تستخدم قيمًا تخمينية ولا مفاتيح تجريبية على الإنتاج.

وفق إعداد المولّد الرسمي، افتح منافذ 443/TCP و80/TCP و7881/TCP و3478/UDP و50000–60000/UDP. إذا عدلت إعداد الوسائط، طابق الجدار الناري مع المنافذ الفعلية. منفذ API الداخلي 7880 يوضع خلف TLS ولا يفتح مباشرة للعامة. راجع [المنافذ والجدار الناري](https://docs.livekit.io/transport/self-hosting/ports-firewall/).

## ربط نخب

### تشغيل LiveKit على نفس VPS الموقع

يمكن تشغيل خدمة LiveKit وRedis على نفس VPS، بشرط توفر الموارد والشبكة المناسبة لعدد المشاركين. افحص الحمل وسعة نقل البيانات قبل اعتمادها؛ نجاح تشغيل الخدمة لا يثبت جودة المكالمات تحت الحمل.

1. حدّد اسمًا فرعيًا لخادم LiveKit واسمًا آخر لـTURN، ووجّههما إلى عنوان الخادم الفعلي. الأسماء تُعتمد في بيانات النشر ولا تُستنتج من اسم المشروع.
2. أبقِ خدمة الموقع وAPI القائمة، وشغّل LiveKit بخدمة مستقلة ونسخة إصدار محددة. مرّر HTTPS/WSS من البروكسي الحالي إلى API الخاص بـLiveKit على منفذه الداخلي؛ لا تمرّر هذا الاسم إلى API نخب.
3. نسّق TURN/TLS على منفذ 443 مع الموقع. إن كانا يستخدمان نفس IP، يلزم بروكسي TCP يدعم توجيه TLS حسب الاسم (SNI)، أو إعداد مكافئ موثّق. البديل عنوان IP إضافي على نفس VPS. بروكسي HTTP العادي لا يمرّر TURN، واسم فرعي جديد وحده لا يحل تعارض منفذ 443.
   يمكن استخدام TURN/TLS على 5349 مع إبقاء الموقع على TCP/443، لكن هذا لا يغطي الشبكات التي تسمح بـTCP/443 فقط. يمكن تشغيل TURN/UDP على 443 إذا كان المنفذ غير مستخدم لخدمة QUIC؛ UDP وTCP منفذان منفصلان.
4. طابق منافذ UDP وTCP في جدار الخادم وجدار مزوّد الاستضافة مع إعداد LiveKit الفعلي. لا تعرّض Redis أو منفذ التحكم الداخلي للعامة.
5. أضف متغيرات LiveKit التالية إلى API نخب، ثم نفّذ فحوص الاتصال والصوت المذكورة أدناه. أضف Webhook لتحديث الحضور الفعلي في البطاقات.

لا تشغّل سكربت المولّد الرسمي دون دمج إعداداته مع الموقع القائم؛ إعداد المولّد يستخدم Caddy لاستقبال HTTPS وTURN، وقد يتعارض مع البروكسي الذي يستقبل 80 و443 بالفعل. راجع [دليل الخوادم الافتراضية](https://docs.livekit.io/transport/self-hosting/vm/) و[متطلبات TURN/TLS](https://docs.livekit.io/transport/self-hosting/deployment/).

### متغيرات API

اضبط متغيرات الخادم التالية في بيئة تشغيل API، خارج Git:

```dotenv
LIVEKIT_URL=
LIVEKIT_API_KEY=
LIVEKIT_API_SECRET=
```

ضع عنوان WSS الفعلي في `LIVEKIT_URL`، ومفاتيح الخادم نفسه في المتغيرين الآخرين. لا تضفها إلى متغيرات Vite أو إلى تطبيق الجوال. يقبل التطوير المحلي فقط WS على loopback. لا تحتاج قاعدة البيانات إلى migration لهذا الربط.

شغّل `node scripts/check-livekit.mjs --configuration-only` لفحص الصيغة دون اتصال، ثم `node scripts/check-livekit.mjs` لفحص الوصول والمصادقة دون إنشاء غرفة أو تعديل بيانات. لا تُطبع المفاتيح أو الرموز في النتيجة.

## التحقق قبل الاعتماد

- ادخل الغرفة بحسابين مصرح لهما، وافحص الصوت في الاتجاهين على الكمبيوتر والجوال عبر شبكتين مختلفتين.
- أبقِ المكالمة أكثر من خمس دقائق، واقطع الشبكة مؤقتًا للتحقق من استعادة الاتصال.
- تحقق من رفض الحساب غير المرتبط بالحلقة، ومن منع دخول الغرفة المغلقة، ومن خروج المشاركين عند إغلاق المنشئ لها.
- تحقق من عمل TURN عندما تمنع الشبكة UDP، ومن تحمل عدد المشاركين المستهدف. نجاح فحص API وحده لا يثبت وصول الصوت.

في الاستضافة الذاتية لا يُلغى رمز سبق إصداره بمجرد حذف غرفة. قد يعيد حامل الرمز إنشاء غرفة LiveKit قبل انتهاء صلاحيته؛ لذلك تبقى صلاحية الانضمام قصيرة ويرفض API إصدار رمز جديد للغرفة المغلقة. راجع [دورة حياة الرموز](https://docs.livekit.io/frontends/reference/tokens-grants/).

حالة التفعيل الفعلية وأسماء النطاقات والمنافذ والخدمات محفوظة في `data1.yml`. تنفيذ التفعيل يحتاج طلبًا صريحًا وفق تعليمات المشروع.

## تحديث بطاقات المكالمات عند الدخول والخروج

يدعم API الآن استقبال الأحداث الموقعة على `POST /api/livekit/webhook`. إذا كانت الاستضافة تضيف بادئة قبل `/api`، استخدم رابط API العام الفعلي مع تلك البادئة. لا تحتاج إلى فتح هذا المسار بحساب مستخدم؛ يتحقق الخادم من توقيع LiveKit ومن تطابق جسم الطلب قبل اعتماد الحدث.

في إعداد خادم LiveKit أضف، مع استبدال القيم بين الأقواس بالقيم الفعلية:

```yaml
webhook:
  api_key: '<نفس LIVEKIT_API_KEY في API>'
  urls:
    - '<عنوان API العام>/livekit/webhook'
```

هذا هو [إعداد Webhooks الرسمي](https://docs.livekit.io/intro/basics/rooms-participants-tracks/webhooks-events/). يجب أن يصل الطلب إلى API دون تغيير جسمه، بنوع `application/webhook+json` ومع ترويسة `Authorization`. يبقى السر في بيئة API وإعداد LiveKit فقط.

استخدم رابط HTTPS النهائي للـWebhook دون تحويل إلى صفحة دخول أو إعادة توجيه. لا تعِد إنشاء JSON في proxy أو Worker، ولا تحذف `Authorization`. يسجل الطلب الصحيح 204، والتوقيع الناقص أو الجسم المعدل 401، ونوع المحتوى الخاطئ 415، والجسم الأكبر من 64 KiB خطأ 413. نقص إعداد LiveKit يعيد 503 حتى يمكن تمييزه عن رفض التوقيع. لا تسجل جسم الحدث أو قيمة التوقيع أثناء التشخيص.

### Nginx

يسمع المتصفح التغييرات عبر `GET /api/calls/events`. قد يختلف المسار العام ببادئة الاستضافة. يوجد إعداد جاهز في [livekit-sse.inc.conf](../config/nginx/livekit-sse.inc.conf)، يضاف **داخل location المخصص للمسار العام الفعلي** بعد نسخه إلى مسار إعدادات Nginx المعتمد. إن كان المسار يرث location عام للـAPI، أنشئ له location مطابقاً تماماً مع نفس `proxy_pass` وإعادة كتابة المسار وترويسات المصادقة وسياق المجمع المستخدمة فعلياً؛ لا تخمّن upstream أو تحذف بادئة API. لا تنسخ location عاماً يغير بقية الطلبات.

محتوى الإعداد:

```nginx
proxy_http_version 1.1;
proxy_buffering off;
proxy_cache off;
gzip off;
proxy_read_timeout 75s;
```

لا تضف `proxy_set_header` منفردة تتسبب في فقدان ترويسات location الأصلية. حافظ على `Authorization` و`Cookie` و`X-Registration-Number` و`X-Nukhab-Native`. إذا كانت هناك وحدة ضغط إضافية مثل Brotli، استثنِ هذا المسار بإعداد الوحدة المثبتة. لا تغيّر `Content-Type` إلى HTML، ولا تحذف أو تستبدل `Cache-Control` الذي يرسله API: `private, no-store, no-cache, no-transform`. نبضة SSE كل ثانيتين تبقي الاتصال نشطاً، و`proxy_read_timeout` يقيس الانتظار بين قراءتين من upstream. بعد اعتماد الوجهة وأخذ نسخة إعداداتها شغّل `nginx -t` قبل إعادة التحميل. راجع [توثيق بروكسي Nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_buffering).

### Cloudflare

طبّق الاستثناء على المضيف والمسار العام الفعليين فقط. تعبير المطابقة في القاعدتين، بعد استبدال القيم بين الأقواس:

```text
(http.host eq "<المضيف الفعلي>" and http.request.uri.path eq "<المسار العام الفعلي لـ calls/events>")
```

- **Cache Rule:** اختر **Cache eligibility → Bypass cache**. تأكد بواسطة Cloudflare Trace من أن القواعد المتداخلة لا تعيد تفعيل التخزين. راجع [إعدادات Cache Rules](https://developers.cloudflare.com/cache/how-to/cache-rules/settings/).
- **Configuration Rule:** اختر **Response Body Buffering → None** لنفس التعبير. قيمة API المكافئة داخل `action_parameters` هي `"response_body_buffering": "none"`. يمنع ذلك تجميع جسم استجابة SSE وفحصه في هذا المسار فقط؛ لا تعطّل فحص أجسام طلبات التسجيل أو بقية الموقع. راجع [إعدادات Configuration Rules](https://developers.cloudflare.com/rules/configuration-rules/settings/#response-body-buffering).
- حافظ على `text/event-stream` وترويسات منع التخزين والتحويل. `no-transform` يمنع التحويل، لكنه لا يكفي وحده لمنع التجميع بغرض الفحص. راجع [فحص جسم الاستجابة والتدفق](https://developers.cloudflare.com/rules/configuration-rules/response-body-inspection/).
- إذا كان Worker أو Snippet يعترض المسار، يجب أن يمرر stream مباشرة؛ قراءة الجسم كاملاً بـ`text()` أو `json()` تؤخر الأحداث حتى اكتماله. لا تغيّر DNS أو تعطّل حماية الموقع كاملة لأجل هذا الاستثناء.

### فحص التدفق بعد التفعيل

يوجد فاحص للقراءة فقط: `node scripts/check-call-stream.mjs`. مرر إليه المتغيرات في جلسة تشغيل آمنة دون كتابتها في Git أو سطر الأوامر أو السجلات:

| المتغير | القيمة |
| --- | --- |
| `CALLS_SSE_URL` | رابط HTTPS النهائي للمسار العام لـ`calls/events` |
| `CALLS_SSE_AUTHORIZATION` | `Bearer` ورمز حساب مصرح له، لتطبيق الجوال |
| `CALLS_SSE_COOKIE` | Cookie جلسة حساب مصرح له، بديل عن Bearer للويب |
| `CALLS_SSE_REGISTRATION_NUMBER` | رقم تسجيل المجمع الذي يرسل معه التطبيق الطلب |

يلزم أحد متغيرَي المصادقة. الفاحص لا يقرأ `.env` تلقائياً، ولا يطبع المشاركين أو الترويسات أو الرموز. يتحقق من رفض الطلب بلا جلسة، ومن 200 للحساب المصرح له، ونوع الاستجابة وترويسات منع التخزين والتحويل، ووصول القائمة ثم نبضة أو تحديث خلال خمس ثوانٍ لكل إطار. يرفض إعادة التوجيه والضغط الظاهر والاستجابة المخزنة أو المغلقة أو المتأخرة، وينهي اتصاله عند انتهاء الفحص. شغّله على المسار المحلي ثم بعد Nginx ثم من خلال Cloudflare لتحديد الطبقة التي تؤخر البث. نجاحه يثبت تدفق SSE؛ لا يثبت وحده تفعيل Webhook أو وصول الصوت.

للتحقق النهائي، افتح بطاقات المكالمات بحساب مصرح له على جهاز، وادخل الغرفة ثم اخرج منها على جهاز آخر وشبكة أخرى. يجب أن تتغير البطاقات دون إعادة تحميل، وأن يظهر دخول الطالب فقط بعد اكتمال اتصال الوسائط. تأكد من وصول أحداث `participant_joined` و`participant_left` إلى API بنتيجة 204، ورفض حدث بتوقيع خاطئ بـ401، ثم إغلاق SSE عند انتهاء الجلسة أو سحب صلاحية المكالمات. يمكن متابعة نوع الحدث والحالة والتوقيت دون تسجيل محتواه أو توقيعه.

الأحداث تنبه اتصالات SSE داخل عملية API نفسها، وتعيد قراءة الموجودين من LiveKit ضمن صلاحيات كل حساب. يبقى فحص دوري كل ثانيتين لاستعادة الحالة إذا ضاع حدث. إذا كانت الاستضافة تشغل عدة نسخ API، يلزم توزيع الأحداث بينها عبر قناة مشتركة للحصول على التحديث الفوري في كل النسخ؛ النسخ الأخرى تستعيد الحالة بالفحص الدوري حاليًا.

قبل تفعيل أحداث الحضور خارجيًا، تحقق من وجود مسار Webhook وSSE في نسخة API المنشورة؛ نجاح ربط الصوت وحده لا يثبت نشر هذين المسارين. حدّد الوجهة المعتمدة، وخذ نسخة إعداد LiveKit وreverse proxy، ثم طبّق الإعداد وأعد تشغيل الخدمات المحددة وتحقق من الصوت والأحداث.
